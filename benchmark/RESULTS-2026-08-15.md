# End-to-end benchmark report — 2026-08-15

> Historical result, superseded by
> [the 2026-08-17 release benchmark](RESULTS-2026-08-17.md). This file predates
> the corrected concurrency and formal-plan protocol and must not be used as a
> current performance claim.

These measurements were produced entirely from this repository's pinned SQL,
preparation scripts, Parquet data, extension, and native DataFusion baseline.
Query time starts before SQL parsing/planning and ends after complete Arrow
output materialization. Bloom transfer, sampling, materialization, P1, joins,
aggregates, and output are all included; offline data preparation is excluded.

## Environment

- DataFusion 54.1.0, Rust 1.92.0, release profile
- Linux 6.1, Intel Xeon Platinum 8474C
- one DataFusion target partition, Arrow batch size 65,536
- JOB May 2013 IMDB snapshot; TPC-H scale factor 10
- optional Parquet row-location mode enabled

## Scan-stage alignment check

An aligned hot-cache JOB 16a diagnostic on this machine measured DataFusion
Bloom transfer at 224.817 ms and the complete query at 242.578 ms. The
corresponding DuckDB Bloom diagnostic measured transfer at 211.071 ms and the
complete query at 219.893 ms. The transfer-stage gap is about 6.5%; this is a
cross-engine diagnostic rather than a claim that the two benchmark harnesses
are identical.

The main scan fixes behind this result are:

- vectorized dense-integer membership with nulls rejected in the same pass;
- sequential application of multiple membership predicates;
- parallel file groups only for partition-local table plans;
- materialized full-column handoff when it is narrower than stable row ids;
- two-pass row-location discovery only for selective or genuinely wide inputs;
- an Arrow scan boundary that keeps membership out of the Parquet decoder;
- safe integer equality/min-max hints retained for Parquet page pruning.
