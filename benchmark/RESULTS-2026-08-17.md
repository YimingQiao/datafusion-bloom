# Release benchmark — 2026-08-17

This report supersedes the performance tables dated 2026-08-16. Those reports
remain useful design history, but they predate the final single-thread runner,
the common string representation, the strong Parquet baseline, and the strict
separation between Bloom's transfer P0 and DataFusion's native formal plan.

## Result

| Workload | Queries | DataFusion | Bloom | Workload speedup | Query geomean | Faster queries |
|---|---:|---:|---:|---:|---:|---:|
| JOB | 113 | 96.940 s | 65.291 s | **1.485x** | **1.436x** | 93/113 |
| TPC-H SF10 | 22 | 79.147 s | 68.728 s | **1.152x** | **1.133x** | 14/22 |

The elapsed columns are sums of per-query medians. All 135 Baseline/Bloom
fingerprints matched. RowLocations was disabled; every retained handoff used
Bloom's normal FullRows semantics.

The complete per-query tables are checked in as
[JOB TSV](results/job-2026-08-17.tsv) and
[TPC-H TSV](results/tpch-sf10-2026-08-17.tsv).

## Measurement contract

- Apache DataFusion 54.1.0, release profile.
- One Tokio worker and one DataFusion target partition.
- DataFusion's native 8,192-row Arrow batch size; no batch override.
- Identical Parquet files and session options for Baseline and Bloom.
- General Parquet filter pushdown and reordering enabled for both engines.
- Ordinary Arrow `Utf8` selected for both engines as the temporary DataFusion
  54.1 compatibility setting described below.
- One untimed alternating Baseline/Bloom pair, followed by three alternating
  measured pairs per query; the reported value is each side's median.
- One long-lived context per engine. A prepared immutable-source sample is
  built once per source and sample size and reused across queries.
- The timer starts before SQL parsing and physical planning and stops only
  after the complete Arrow output has been consumed and fingerprinted.
- Context creation, table registration, data generation, and the untimed
  prepared-sample warmup are outside query elapsed time.

Bloom's `plan_ms` includes transfer initialization, transfer scans, membership
construction, FullRows collection, and physical compaction. It is not merely
optimizer CPU. `exec_ms` is the unchanged formal DataFusion plan after its
participating table leaves have been replaced.

The benchmark host was Linux 6.1 on a dual-socket Intel Xeon Platinum 8474C
machine. Although the host exposes 192 logical CPUs, each run was restricted
by the runner to one Tokio worker and one target partition. The toolchain was
Rust 1.92.0. JOB Parquet occupied 1.4 GiB and TPC-H SF10 Parquet 2.3 GiB.

## Cost split

| Workload | DataFusion plan | DataFusion execute | Bloom transfer/plan | Bloom formal execute |
|---|---:|---:|---:|---:|
| JOB | 0.766 s | 96.175 s | 62.168 s | 3.116 s |
| TPC-H SF10 | 0.113 s | 79.032 s | 36.084 s | 32.625 s |

This split is useful but should not be read as an alternative benchmark.
Transfer is real query work and is included in every Bloom elapsed value. JOB
shows the intended trade: transfer spends 62.2 seconds preparing compact table
inputs and reduces formal execution from 96.2 seconds to 3.1 seconds. TPC-H is
less join-dense, so transfer has less room to amortize.

The strongest JOB improvements include 21a–21c (`4.89x`–`5.03x`), 27a–27c
(`3.79x`–`3.95x`), and 16c (`2.90x`). The worst stable JOB cases remain in the
complete result: 2c (`0.324x`), 6b/6c (`0.568x`/`0.570x`), and 10c (`0.645x`).
Their formal joins are nearly free after transfer, but their original queries
are too short for the transfer scans and materialization to amortize.

TPC-H Q19 improves by `2.585x`; Q8, Q10, Q21, and Q9 improve by `1.375x`,
`1.355x`, `1.289x`, and `1.265x`. Q12 is the only material regression at
`0.960x`. Queries without an effective handoff are approximately neutral.

## Native formal-plan correction

Transfer table operators must be independently executable, so Bloom's P0
disables DataFusion runtime dynamic filters. An earlier implementation also
used that P0 as the formal plan. This accidentally removed join-owned dynamic
filters from untouched Parquet scans and violated the intended two-stage
boundary.

The final design builds two plans with the same native join tree:

1. P0 disables runtime dependencies and exists only for transfer;
2. the formal plan retains DataFusion's native dynamic filters and receives
   only the table replacements that produced an actual handoff.

The stable TPC-H checks below show the effect. They use the same benchmark
protocol before and after the correction.

| Query | Before | After | Explanation |
|---|---:|---:|---|
| Q4 | 0.843x | 0.999x | zero handoffs; native dynamic filter restored |
| Q18 | 0.644x | 1.015x | zero handoffs; two native dynamic filters restored |
| Q20 | 0.811x | 0.994x | untouched formal inputs retain native filtering |

This correction also removes false positive-looking gains: Q11 changed from
`1.254x` to `0.997x`. The remaining headline therefore reflects transfer and
handoff behavior rather than a different join runtime configuration.

## Why the benchmark temporarily uses Utf8

DataFusion 54.1 maps SQL and Parquet strings to Arrow `Utf8View` by default.
During the initial audit, multi-layer high-fanout joins repeatedly carried and
cloned large backing-buffer lists through the byte-view `take` path. Under
otherwise matched single-query settings, stock DataFusion JOB 9d took 235.184
seconds with `Utf8View` and 0.983 seconds with ordinary `Utf8`. JOB 16a took
371.743 seconds versus 26.675 seconds. The native-view audit was stopped while
16b was still running after more than 30 minutes, so there is deliberately no
full-workload `Utf8View` headline.

Profiling localized the cliff to Arrow byte-view selection and buffer lifetime,
not Bloom membership. The runner therefore sets both of these options to
`false` for Baseline and Bloom before table registration:

```text
sql_parser.map_string_types_to_utf8view
execution.parquet.schema_force_view_types
```

This makes the Bloom comparison fair but is not DataFusion 54.1's native string
default, so every result header prints `string_type=Utf8`. `--utf8view`
restores the native mapping for sensitivity testing. This workaround does not
change DataFusion's batch size and does not enter Bloom's transfer scheduler or
materialization policy.

## Reproduction

Prepare each dataset from this repository, then run:

```bash
benchmark/scripts/prepare-job.sh
cargo bench --bench workload -- \
  --workload job --threads 1 --warmups 1 --runs 3 \
  --parquet-pushdown

benchmark/scripts/prepare-tpch.sh 10
cargo bench --bench workload -- \
  --workload tpch --scale-factor 10 --threads 1 --warmups 1 --runs 3 \
  --parquet-pushdown
```

Add `--utf8view` only for the native string-representation sensitivity run.
The runner prints the effective batch size, string type, context lifetime,
membership placement, handoff policy, and Parquet setting in its result header.
