# Benchmark audit and corrected results — 2026-08-16

> Historical audit, superseded for performance claims by
> [the 2026-08-17 release benchmark](RESULTS-2026-08-17.md).

> This file is retained as the concurrency-fairness audit. The implementation
> and measurements were subsequently updated by the
> [materialization redesign](RESULTS-2026-08-16-MATERIALIZATION.md); use that
> report for current performance numbers.

This report supersedes every earlier result recorded under this date. The
previous headline numbers (JOB 9.148x and TPC-H SF10 2.177x) were invalidated
by a concurrency mismatch described below. They must not be cited as Bloom
speedups.

## What the benchmark measures

All data, SQL, preparation scripts, and binaries are owned by this repository.
The timer starts before SQL parsing/planning and stops after complete Arrow
output materialization. Sampling, transfer scheduling, handoff creation, P1,
joins, aggregates, and output are included. Fingerprinting and diagnostic plan
formatting happen after the timer.

Baseline and Bloom alternate first/second execution order and use identical
DataFusion `SessionConfig` values. Every pair must produce the same complete,
order-independent output fingerprint. The default is a long-lived workload:
query-independent prepared Parquet samples are built once per source and
sampling size in the Bloom `SessionContext`, then reused by later queries.

Environment:

- DataFusion 54.1.0, Rust 1.92.0, release profile
- Linux 6.1, Intel Xeon Platinum 8474C
- 96 physical cores / 192 logical CPUs; two NUMA nodes
- Arrow batch size 65,536
- JOB May 2013 IMDB snapshot, 1.4 GiB Parquet, 113 canonical queries
- TPC-H-derived SF10, 2.3 GiB ZSTD(3) Parquet, 22 SQLBench-H queries
- zero warmups and one complete measured pair per query for the full audit

These are exploratory full-workload measurements, not confidence intervals.
Use multiple warmups/runs and controlled machine isolation for publication.

## Fairness defect found and fixed

The old runner interpreted `--threads 1` only as DataFusion
`target_partitions=1`, while `#[tokio::main]` still created a multi-thread
runtime with access to all host CPUs. Baseline scans had one P0 file group, but
Bloom's `FullRows` path manually replaced that grouping with one partition per
physical file (typically 2–5 files per JOB table and 32 per large TPC-H table).
Consequently the nominally single-thread Bloom path executed scan partitions
concurrently while Baseline could not. The bias affected Bloom only and was
large enough to explain the implausible scan time.

The correction has two parts:

1. `--threads 1` now uses Tokio's current-thread runtime; `--threads N` uses
   exactly N Tokio workers as well as `target_partitions=N`.
2. `FullRows` no longer expands Parquet file groups. It preserves the P0 scan
   partition count selected by DataFusion.

All 29 library/integration tests, `cargo check --all-targets`, and clippy with
warnings denied pass after the change.

## Corrected complete workloads

The workload speedup is the ratio of summed complete query times. Geomean is
the geometric mean of the 113 or 22 individual speedups and therefore does not
let a handful of long queries dominate as strongly.

| Workload | Threads | DataFusion | Bloom | Workload speedup | Query geomean | Faster queries |
|---|---:|---:|---:|---:|---:|---:|
| JOB | 1 | 346,719.599 ms | 105,679.118 ms | 3.281x | 1.243x | 57/113 |
| TPC-H-derived SF10 | 1 | 71,885.070 ms | 69,886.039 ms | 1.029x | 0.986x | 10/22 |
| JOB | 16 | 40,664.086 ms | 22,005.954 ms | 1.848x | 1.062x | 48/113 |
| TPC-H-derived SF10 | 16 | 8,274.813 ms | 7,996.169 ms | 1.035x | 0.978x | 7/22 |

Default `FullRows` was used and RowLocations was disabled. The 16-thread
results demonstrate that the one-thread totals are not representative of
normal parallel DataFusion throughput: Baseline becomes 8.53x faster on JOB
and 8.69x faster on TPC-H-derived SF10. Bloom also scales, but its JOB workload
speedup falls because native parallel execution reduces the absolute cost of
the bad Baseline join plans that Bloom avoids.

TPC-H is presently neutral: the summed result is about 1.03x at both thread
counts while the per-query geomean is slightly below 1.0x. Q17 is the clearest
win (1.978x at one thread and 1.863x at 16); Q2 and Q3 regress because transfer
and FullRows materialization cost more than the formal join work they remove.
This workload does not support a claim of broad TPC-H acceleration yet.

## Sanity checks and cache boundary

TPC-H Q1 contains no join and creates no Bloom handoff. In a separate strict
one-thread run with one warmup and three measured pairs, Baseline took
5,764.525 ms and Bloom 5,758.841 ms (1.001x). This negative control shows that
the timer and runtime do not intrinsically favor Bloom after the fix.

`PreparedSampleCache` intentionally belongs to the Bloom planner and persists
for its `SessionContext`. This matches the extension's service lifecycle: an
immutable table sample is prepared once and reused. The optional
`--fresh-context-per-query` mode is diagnostic only. With no warmup and one run
on JOB 1a, 16a, and 32a, fresh sessions measured:

| Query | DataFusion | Bloom | Speedup |
|---|---:|---:|---:|
| 1a | 132.103 ms | 613.182 ms | 0.215x |
| 16a | 25,723.782 ms | 2,500.789 ms | 10.286x |
| 32a | 22.017 ms | 351.074 ms | 0.063x |

This quantifies cold sample construction without changing the primary
long-lived-workload semantics. It also shows why very short queries require a
handoff/activation profitability guard: fixed transfer work cannot amortize.

## Why native DataFusion JOB is sometimes genuinely slow

The remaining large Baseline times are execution, not SQL setup or Parquet
reader overhead. For JOB 16a, `EXPLAIN ANALYZE` metrics showed approximately
1.07 billion cumulative intermediate HashJoin output rows and about 34,082%
fanout; one HashJoin build consumed roughly 24 seconds in the strict
one-thread run. The canonical SQL join tree plus DataFusion's chosen physical
plan causes this intermediate explosion. Bloom reduces the table inputs before
running the same stock formal joins, so the q16/q17 family supplies most of the
summed JOB gain. At 16 threads, examples include q16a 20.855x and q17c 24.634x.

Many ordinary JOB queries are neutral or slower. That is why the honest result
is both 1.848x summed speedup and only 1.062x query geomean at 16 threads, not
the old 9.148x headline.

## External DataFusion context

There is no hardware-independent number for "DataFusion speed." Apache's
[benchmark repository](https://github.com/apache/datafusion-benchmarks)
likewise uses derived TPC workloads, multipart Parquet, and individual query
timings. Apache reported DataFusion 43 as the fastest engine in a hot
ClickBench run over 14 GB of partitioned Parquet on a 16-vCPU machine, while
also noting DuckDB was slightly faster in the cold run:
[DataFusion single-node Parquet report](https://datafusion.apache.org/blog/2024/11/18/datafusion-fastest-single-node-parquet-clickbench/).
That result establishes that DataFusion's Parquet engine is competitive; it
does not predict canonical multi-join JOB plans.

DataFusion itself also treats immutable metadata caching as normal persistent
engine state. Version 52 added a file-statistics cache and expanded native hash
join dynamic filtering:
[DataFusion 52 release](https://datafusion.apache.org/blog/output/2026/01/12/datafusion-52.0.0/).
Bloom's once-per-session prepared-sample reuse is therefore reported
explicitly rather than disabled, with the fresh-session mode retained to
measure its cold cost.

## Reproduction

```bash
# Primary long-lived workload, strict single thread
cargo bench --bench workload -- \
  --workload job --threads 1 --warmups 0 --runs 1
cargo bench --bench workload -- \
  --workload tpch --scale-factor 10 --threads 1 --warmups 0 --runs 1

# Equal 16-worker comparison
cargo bench --bench workload -- \
  --workload job --threads 16 --warmups 0 --runs 1
cargo bench --bench workload -- \
  --workload tpch --scale-factor 10 --threads 16 --warmups 0 --runs 1

# Diagnostic cold-query boundary
cargo bench --bench workload -- \
  --workload job --queries 1a,16a,32a --threads 1 \
  --warmups 0 --runs 1 --fresh-context-per-query
```

## Current decision

The benchmark harness is now fair with respect to CPU workers and scan
partitions. `FullRows` remains the default; RowLocations remains optional and
experimental. Prepared samples remain once-per-session reusable state, as
intended.

The current extension has a meaningful JOB throughput result, especially for
join plans with severe intermediate blow-up, but it does not yet accelerate
TPC-H broadly. The next performance work should target transfer profitability
and materialization cost on q2/q3/q19 and short JOB queries, while preserving
the strong q16/q17 reductions and the corrected benchmark controls.
